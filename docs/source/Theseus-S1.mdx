# EVO-RL Adaptation for Theseus S1 Robotic Arm Operation Guide

Based on the existing **EVO-RL** framework, the adaptation for the **Theseus S1 robotic arm** has been completed.

Through this adaptation, Theseus S1 users (whether operating a single arm or dual arms) can now seamlessly integrate into the EVO-RL closed-loop reinforcement learning workflow. This guide will walk you through the entire process: from initial hardware configuration, multi-view camera mounting, and expert data collection, to Value Function training, Advantage-Conditioned Policy (ACP) fine-tuning, and finally, model evaluation and deployment with a "Human-in-the-loop" mechanism.

> **Applicable Hardware:** The Theseus S1 robotic arm currently uses **V2** version **USB serial** communication. **V1 / V2 Differences:** The V1 version used CAN interface for the main arm, while the V2 version uses USB serial. We have fully transitioned to the V2 version; the V1 version is no longer supported.
>
> **Hardware Calibration Note:** The Theseus S1 robotic arm is pre-calibrated at the underlying SDK level. Therefore, when using the EVO-RL framework, **no secondary calibration is required at the framework level** (you will see that the `--robot.require_calibration=false` and `--teleop.require_calibration=false` parameters have been explicitly set to `false` in all subsequent startup commands).

## Hardware Setup

### S1 Series (V1 / V2) Version Differences

> **[!] Critical Version Differences:**
> 
> - **V1 Version**: Uses **CAN** interface for communication (Legacy version, no longer in use).
>     
> - **V2 Version**: Uses **USB** serial for communication (e.g., `/dev/ttyUSB0`, `/dev/ttyUSB1`). All commands below are based on V2.

### Hardware Types and Configuration

The Theseus S1 hardware is categorized into three types:
- **leader**: The master arm, used by human operators for teleoperation.
- **follower**: The slave arm, the entity that executes tasks.
- **mix**: A combo arm (integrated master-slave).

#### Compatibility and End-Effector (`end_effector`) Configuration:

1. **Master-Slave Mode (Leader + Follower)**:
   - When using **leader** as the master arm, it can be paired with either a **follower** or a **mix** arm as the slave.
   - If the slave arm is a **follower**, its `end_effector` must be set to `gripper`.
   - If the slave arm is a **mix** arm, its `end_effector` must be set to `mix`.

2. **Combo Arm Scheme (Integrated Master-Slave)**:
   - Uses only the combo arm for operation (i.e., "one arm does it all," no extra leader arm required).
   - In this setup, the `end_effector` for both `robot` (robot side) and `teleop` (teleoperation side) must be set to `mix`.

> [!NOTE]
> **Robotic Arm Connection Order:** After unplugging all four arms, please plug their USBs into the computer in the following order: **left follower, right follower, left leader, right leader**. The system default mappings are **USB0, USB1, USB2, USB3**, respectively (i.e., left follower = `/dev/ttyUSB0`, right follower = `/dev/ttyUSB1`, left leader = `/dev/ttyUSB2`, right leader = `/dev/ttyUSB3`).

### System Environment and Device Check

Before running any commands, you must grant appropriate read/write permissions to the USB/Video ports:

```Bash
# Check if devices are mounted successfully
ls -l /dev/ttyUSB*
ls -l /dev/video*

# Grant permissions for serial ports and cameras
sudo chmod 666 /dev/ttyUSB*
sudo chmod 666 /dev/video*
```

**Parameter Notes:**
- `<LEFT_FOLLOWER_USB_PORT>` / `<RIGHT_FOLLOWER_USB_PORT>`: The corresponding USB serial device name (e.g., `/dev/ttyUSB0`, `/dev/ttyUSB1`).
- For additional USB master devices, use the same `/dev/ttyUSB*` device naming convention.

Before data collection, verify the camera index numbers. You can use the following command to find and test your cameras:

Retrieve the **Id** (12-digit serial number, e.g., `352122272634`) from the console output.

**Parameter Notes:**
- `--output-dir`: The output directory for the tested camera images.

> **Camera Assignment Strategy (Dual-Arm Mode):**
> - `left` (Left arm view): Mount under `--robot.left_arm_config.cameras`.
> - `right` (Right arm view) and `middle` (Global view): Mount under `--robot.right_arm_config.cameras`.

> **Camera Assignment Strategy (Single-Arm Mode):**
> - `wrist` (Single arm view) and `middle` (Global view): Mount under `--robot.cameras`.

## Architecture Overview

Hardware configurations available for dual-arm and single-arm scenarios:

Use `lerobot-human-inloop-record` to collect the first round of reinforcement learning data.

> - For the first round of data, as no model has been trained yet, you must perform full manual control. Therefore, theoretically, all episodes should be marked as successful (press **s** for every episode).

## 3. Value Function Training

After collecting the data, you need to train a Value Function.

```Bash
lerobot-value-train \
    --dataset.repo_id=<DATASET_PATH> \
    --dataset.video_backend=pyav \
    --value.type=pistar06 \
    --value.dtype=bfloat16 \
    --batch_size=4 \
    --num_workers=0 \
    --output_dir=outputs/value_train/<RUN_NAME> \
    --job_name=<JOB_NAME> \
    --wandb.enable=false
```

**Parameter Notes:**
- `--dataset.video_backend`: Video processing backend, `pyav` is recommended for better performance.
- `--value.type`: The value function model type to use (currently supports codes like `pistar06`).
- `--value.dtype`: Data precision for training and inference; `bfloat16` can significantly reduce VRAM usage.
- `--batch_size`: Batch size per training iteration.
- `--num_workers`: Number of data loading threads. To avoid interference between multi-threading and hardware communication, setting this to `0` for main-thread synchronization is safer.
- `--output_dir`: Directory to save logs, model checkpoints, etc.
- `--job_name`: A recognizable name for the current training task.
- `--wandb.enable`: Whether to enable Weights & Biases (WandB) tracking; can be turned off to save resources.

### Multi-GPU Training

If you have multiple GPUs, you can use `accelerate` to speed up training:

```bash
CUDA_VISIBLE_DEVICES=<GPU_ID_LIST> accelerate launch \
  --multi_gpu \
  --num_processes=<NUM_GPUS> \
  --mixed_precision=bf16 \
  $(which lerobot-value-train) \
  --batch_size=32/<NUM_GPUS> \
  <VALUE_TRAIN_ARGS>
```

**Multi-GPU Training Parameters:**
- `CUDA_VISIBLE_DEVICES`: Specify visible GPUs (e.g., `0,1,2,3`).
- `--num_processes`: Specify the number of GPUs to parallelize.
- `--mixed_precision`: Mixed-precision training mode, `bf16` is recommended.
- `--batch_size`: Batch size **per GPU**. To maintain a total batch size of 32, it is recommended to set this to `32 / <NUM_GPUS>`.

## 4. Value Function Inference

Once training is complete, use Value Inference to tag the dataset with ACP (Advantage-Conditioned Tags):

```Bash
lerobot-value-infer \
```

**Parameter Notes:**
- `--inference.checkpoint_path`: Path to the value model checkpoint used for inferring labels.
- `--runtime.device`: Device for inference (e.g., `cuda`).
- `--runtime.batch_size`: Batch size for batched inference.
- `--acp.enable`: Whether to enable the Advantage-Conditioned Policies (ACP) calculation and helper tagging module.
- `--acp.n_step`: Time window length for calculating cumulative N-step returns.
- `--acp.positive_ratio`: Threshold ratio for marking data as "Advantage-Conditioned". Setting to `0.1`, for instance, tags the top 10% of expert data as "preferred positive".
- `--acp.value_field` / `--acp.advantage_field` / `--acp.indicator_field`: Specifies the column field names in the dataset for inferred value (Value), relative advantage absolute difference (Advantage), and the final confirmed ACP indicator flag.

**Parameter Notes:**
- `--policy.type`: Specify the policy architecture (e.g., `act` for Action Chunking with Transformers).
- `--policy.device`: Device for training (e.g., `cuda`).
- `--acp.indicator_dropout_prob`: Probability of randomly dropping the expert ACP indicator during training (set to `0.3`). - `--policy.push_to_hub`: Whether to upload the final validation model to Hugging Face Hub (set to `false` for local training).

## 6. RL Closed-Loop + Next Round Data Collection (Human-in-the-loop)

> [!IMPORTANT]
> - When the model makes a mistake, press the **i** key to enter human intervention mode, take control to correct the behavior.
> - For the second round and beyond, because a trained model exists, the data consists of model actions + human-corrected actions.
> - You still need to press **s** or **f** at the end of every episode to indicate task success. Failing to press a key defaults to failure, which invalidates subsequent training.

- `--acp_inference.use_cfg`: **(Optional)** Whether to enable Classifier-Free Guidance (CFG). Requires `--acp_inference.enable=true`. **Shortcut Key Table:**

| Key | Function |
| :--- | :--- |
| **i** | Toggle **Intervention Mode** (switch between "Model Auto-Control" and "Manual Takeover") |
| **s** | Mark as **Success** and end the current episode |
| **f** | Mark as **Failure** and end the current episode |
| **→** (Right Arrow) | End the current cycle early (save and move to next episode) |
| **←** (Left Arrow) | End and **Re-record** the current episode (discard data) |
| **Esc** | Stop and exit the entire recording session |

> [!NOTE]
> **Intervention Mode Principles (bi_s1_direct_teleop)**
>
> - **Policy Control (Default)**: `[set_manual_control(False)]` — The action generated by the policy controls the arm movement via `robot.send_action()`, while `teleop.send_feedback()` makes the arm follow the policy.
> - **Human Intervention (Press i)**: `[set_manual_control(True)]` — The teleop calls `gravity()`, allowing manual dragging for correction; the action comes from the current pose read by the teleop.

# Combo Arm Scenarios

## Architecture Overview

Under the combo arm scheme, hardware configurations available for dual-arm and single-arm scenarios:
- Only two mix arms (Combo gripper data collection, combo arms)
- Only one mix arm (Combo gripper data collection, combo arms)

> [!IMPORTANT]
> In the combo arm scheme, no extra leader arm is needed for data collection / teleoperation! Just drag the two combo arms directly.

> [!NOTE]
> **Robotic Arm Connection Order:** After unplugging both combo robotic arms, please plug their USBs into the computer in the order of **left combo arm, right combo arm**. The system default mappings are **USB0, USB1**, i.e., left combo arm = `USB0`, right combo arm = `USB1`.

> [!NOTE] The device paths and camera serial numbers in the commands below are **example placeholders**, please replace them according to your actual hardware connection:
>
> - Left combo arm serial: `/dev/ttyUSB0`, right combo arm serial: `/dev/ttyUSB1`
> - Camera serial numbers: `left=352122271174`, `right=352122272634`, `middle=352122271611`
>
> Camera assignment notes:
>
> - `left` (Left arm view camera) mounted under **left_arm_config**
> - `right` (Right arm view camera) + `middle` (Global view camera) mounted under **right_arm_config**

**Multi-GPU Training Parameters:**
- `CUDA_VISIBLE_DEVICES`: Specify visible GPUs (e.g., `0,1,2,3`).

- `--batch_size`: Batch size **per GPU**. For example, target a total batch size of 32, with 4 GPUs, set it to 8.

## Comparison between Combo Arm and Leader+Follower Schemes

| Feature | Leader+Follower Scheme | Combo Arm Scheme |
| :--- | :--- | :--- |
| Hardware count | 4 arms (2 leader + 2 follower) | 2 arms (one arm two-use) |
| Teleop type | `bi_s1_leader` | `bi_s1_direct_teleop` |
| Robot type | `bi_s1_follower` | `bi_s1_direct` |
| Teaching method | Drag leader | Direct drag combo arm (gravity compensation) |
| Intervention mode | Leader takeover → follower follow | Direct drag combo arm |
| Data format | Identical | Identical |
| Policy compatibility | Identical | Identical |
